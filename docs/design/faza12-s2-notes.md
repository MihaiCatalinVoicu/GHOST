## 1. The Gradle assets hook (the design's §5.4.3, §4.1, §9.1)

`:app/build.gradle.kts` gains the `ptAssets` task (the `ThirdPartyNoticesAsset` pattern, registered for every variant through `androidComponents.onVariants`'s assets source):

- **Inputs**: `ghost/third_party/lyrebird/out/{SHA256SUMS, lyrebird-android-arm64, lyrebird-android-amd64}` as a file collection — *copied only when present*: an input collection of missing files is simply absent (the host/JVM build that has no binaries compiles and runs with PT rejected, §8.4). With no sums file the task emits an empty sums asset and no binaries; PT is then unavailable on that build, which is exactly §8.4's world.
- **The mapping + the drift check**: the in-repo sums name `lyrebird-android-<arch>`; the APK assets are `pt/<abi>/lyrebird` with a regenerated `pt/SHA256SUMS` in the `<hash>  <abi>/lyrebird` format `PtInstaller` parses. A binary whose actual SHA-256 drifts from the in-repo sums **fails the build** (`check`), so a stale `out/` directory can never ship; the check is the same one G-T4 applies to the APK, moved one step earlier.
- **Per ABI, both ABIs**: `arm64-v8a` and `x86_64` are both packaged (Q9), the layout mirroring the jniLibs `abiFilters`; the extraction picks the device's ABI at first PT use (§2). aapt's default deflate is the compression; the measured sizes stand inside the rev-2 pins (§9).
- `:network`'s `ptTestAssets` task generates the byte-identical tree for the emulator probe's test APK (its own copy of the same transformation, so the probe never reads another module's build tree; §7).

Measured on the generated tree (2026-10-17, this session): extracted 7 668 008 B (arm64-v8a, pin 7 668 008) and 7 556 392 B (x86_64, pin 7 556 392); gzip-9 2 899 228 B (pin ≤ 2 899 241) and 3 107 247 B (pin ≤ 3 107 257) — the 13/10-byte gzip deltas against the S0 record are gzip header metadata on byte-identical payloads, both budgets met with room to spare.

## 2. The `:network` extraction (PT-1/PT-2; §5.4.4, §8.2, §8.3)

`PtInstaller` (`android/network/.../PtInstaller.kt`), the pure-JVM core around injected streams:

- **Install**: `pt/<abi>/lyrebird` asset → stream to `lyrebird.tmp` under `filesDir/pt/<abi>/` with a 32 MiB hard cap (an order above the pinned 7.7 MiB; over the cap is refused exactly like a hash mismatch) → SHA-256 against the sums asset → `chmod 700` **on the verified temp file** → atomic rename (`ATOMIC_MOVE`, falling back to a plain replace) → the stamp `.lyrebird.sha256` written with the hash.
- **The versioned stamp, redone on update**: the stamp holds the asset's *hash*, not a flag — an app update whose asset changed mismatches the stamp and forces re-extraction; an unchanged asset makes a repeat `install()` a no-op (PT-U9 pins both, and the chmod count).
- **Fail-closed, typed**: a hash mismatch or a missing/oversized asset deletes the temp file and throws `NetworkException("pt_hash_mismatch")` / `("pt_unsupported_abi")`; the ABI is `Build.SUPPORTED_ABIS.first { it in {arm64-v8a, x86_64} }` (the runtime's own selection when it loaded `libghost_client_net.so`); `installed()` (PT-2) is the cheap stamp check and never throws.
- **Android glue vs the test core**: `forApp(context)` resolves filesDir/ABI/assets; the core takes `(ptRoot, abi, openAsset, chmod700)` so PT-U9 runs on mocked streams; the production chmod is the default `File.setExecutable(true, ownerOnly)` (owner rwx = 700 on the app-private fs), and the device test pins the exact mode via `Os.stat`.
- **Never clearnet, never a second spawn site**: the installer only writes files; the only process ever spawned for PT is arti's ptmgr child inside `ghost-client-net` (G-T6's allowlisted site; S3's gate owns the textual proof).

## 3. The `transport_bridge` migration and the storage facade (§6.3, §6.4, §8.1; ADR-62 point 4)

- **Migration 9** (`Schema.kt`): `CREATE TABLE transport_bridge (line TEXT PRIMARY KEY NOT NULL CHECK (length(line) > 0 AND length(line) <= 1024), added_day INTEGER NOT NULL CHECK (typeof(added_day) = 'integer' AND added_day >= 0)) WITHOUT ROWID` — one additive statement, no rebuild, no data movement, no `REPLACE` paths (§11), so it joins `verifyIntegrity` without further T33 review; the 1 024-char bound is a schema CHECK, not only application code. No `transport_bridge_no_replace` guard: the writer's dedup is `INSERT OR IGNORE` (§6.3's own exemption), recorded in the migration's KDoc and pinned by PT-U8 (the guard's absence and the trigger absence are asserted).
- **The DAO** (`TransportBridgeRepository` in `:storage`, beside the other repositories): `replaceAll` (transactional whole-set replace — the settings screen writes the full list), `list` (`ORDER BY added_day, line`, S2-T6), `delete(line)` (exact, returns whether a row went). Nothing else in the repository ever logs a line (T58's storage half; the table has no foreign keys into engines, so the G-DM2-class enqueue gate extension is not needed — §6.3).
- **The facade** (`BridgeLines` in `:network`, §8.1's "written through :network's repository class"): `set` validates through `TorRelayTransport.validateBridgeLines` (the native call, §0 S2-T1) and stores only the validated, deduped set; `list` returns the stored lines; `delete` removes one exact line. This is the seam Phase 13's paste/QR screen calls (§8.5) and the Q4 host entry drives today. All-or-nothing: a refusal stores nothing (PT-U7).
- **The privacy shape**: the lines live in the SQLCipher database like everything else — no new key, no new table family, the existing `allowBackup="false"`/no-backup posture (D7); nothing crosses the JNI boundary except validated lines into storage and category+index out of a refusal; the four categories are documented in the README table and pinned at both ends (the Rust `categories_are_unique_and_documented` test and `PtErrorCategoriesTest`).

## 4. The reduced auto mode (§6.5, Q6, X-T2; ADR-62 point 5)

- `BootstrapPlan` (org.ghost.sync.android): the epoch's sequence is direct (when `allowDirect()`) then `lines().map(Bridges)`, read at claim time so a line change takes effect next epoch; `claim()` advances, null means exhausted.
- `TorTransportHolder` (where bootstrap orchestration already lives, §8.1): the `forApp` factory claims the next attempt per `create` and throws `NetworkException("tor_bootstrap")` — `BootstrapSpent`'s category — when the plan is exhausted, which `createAndBootstrap` maps like any factory failure: no client is created, the answer is UNAVAILABLE, the caller's backoff gives up; `abort()` resets the plan (a session's end starts the next session's sequence). `nativeCreate` still validates every line at config build (S1): a bad stored line is a `bridge_config` create-time error, never a bootstrap surprise.
- **pt_dir resolution per attempt**: a direct attempt never installs (extraction at first PT use, §5.4.4); the first PT need installs via `PtInstaller` (already-extracted is a stamp check); a refused extraction is remembered **only when PT was needed** — a "no" on the direct path is not final — and fails closed to `pt_dir = null`, so PT lines then meet `PtBinaryMissing` (`bridge_config`), never a half-trusted exec.
- **Never clearnet**: the factory only ever constructs `create(state, cache, bridgeLines = ∅ or one configured line, ptDir)` — PT-U4 pins that every created transport's config is the direct shape or an exact configured line, and the exhaustion/spent-chain/abort-reset behaviour over a scripted factory on real threads.

## 7. The emulator probe (PT-1; §12.1 V-T6 re-run, in-app)

`:network` gains an `androidTest` suite on the plain `DeviceRunner` (the emulator job's runner discipline, `crypto-bridge`'s deviceRunner sources): `PtInstallDeviceTest` drives `PtInstaller.forApp(targetContext)` on a real app-private filesDir — install, the exact `0700` mode via `Os.stat`, the idempotent stamp — and then adjudicates the filesDir exec itself (S0-T7's deferred half). The test APK carries the same generated `pt/` tree as the shipping APK (`ptTestAssets`, §1).

- **API 35 (`ghost-dm-api35`)**: `device tests: 1 run, 0 failed, 0 skipped`.
- **API 29 (`ghost-dm-api29`)**: `device tests: 1 run, 0 failed, 0 skipped`.
- The probe's verdict, identical on both levels (the report lines record it):
  - **Direct `execve` of the filesDir binary is refused**: `Cannot run program …/files/pt/x86_64/lyrebird: error=13, Permission denied`, with the SELinux denial in the audit log: `avc: denied { execute_no_trans } … scontext=u:r:untrusted_app … tcontext=u:object_r:app_data_file` — and, load-bearing for the candidate fix, `avc: granted { execute }` on the same file (mmap-exec is allowed; only exec-as-program is not).
  - **The system-linker indirection answers**: `/system/bin/linker64 <absolute path>/lyrebird -version` → `lyrebird 0.9.0`, no policy complaint: the exec target is a system file, and the binary itself only needs read + the granted mmap-exec.
- **What this means: C-3's filesDir half is refuted as the design words it** (§5.4 point 5's "normal, allowed operation" is true only for targetSdk ≤ 28, the legacy `untrusted_app_27` domains — Termux stayed on targetSdk 28 for exactly this reason; the modern Tor services moved in-process). This is a fired load-bearing assumption of the same class as OA-3: **OA-4** (§0 S2-T7). Everything S2 built — extraction, verification, chmod, the stamp, storage, the auto mode — stands unchanged under either outcome; only the exec mechanism does.
- **OA-4 resolved in this session — option A adopted (design rev 3, §5.4.5).** `ghost-client-net`'s `build_config` now resolves the launch shape via `pt_exec`: `pt_binary` unchanged (existence only), then `pt_linker` — the system dynamic linker for the compiled ABI (`std::env::consts::ARCH`: `aarch64`/`x86_64` → `/system/bin/linker64`; a future 32-bit ABI → `/system/bin/linker`), existence-verified on Android, typed `TransportError::PtLinkerMissing` (config class → `bridge_config`, pinned in `categories.rs`'s mapping test) when absent. The ptmgr transport config becomes `path = <linker>`, `arguments = [<pt_dir>/lyrebird]` (ptmgr 0.46's `TransportConfigBuilder.arguments` — S0-T4's `Command::new(path).args(arguments)` reading; config-only, no arti patch). Pinned in the new Rust unit test `pt_launch_shape_is_the_system_linker_plus_the_binary_argument`. **Measured correction:** the gate x86_64 images carry no `/system/bin/linker` at all (`ls -l /system/bin/linker*` → `linker64` and `linker_asan64` only, symlinks into `/apex/com.android.runtime`), so the resolution is ELF-class-based, not ABI-name-based — the "linker for x86_64" mapping would refuse every launch on the very images that prove the workaround.
- **The arm64 probe via translation (this session, API 35): translation ABSENT.** The hypothesis that the Google x86_64 API 30+ images carry ARM-to-x86 translation does not hold for the gate image: `ro.product.cpu.abilist` = `x86_64` and `ro.product.cpu.abilist64` = `x86_64` only, no `ro.dalvik.vm.native.bridge`. Pushed `lyrebird-android-arm64` (7 668 008 B, the pinned binary) to `/data/local/tmp`, chmod 755: direct exec answers `/system/bin/sh: …: not executable: 64-bit ELF file`; `/system/bin/linker64 /data/local/tmp/lyrebird-arm64 -version` answers `error: "…" is for EM_AARCH64 (183) instead of EM_X86_64 (62)` (bionic's linker refuses the foreign machine itself, before any translation could apply). **Verdict: the emulator cannot answer the arm64 static-through-bionic question; the arm64 exec stays owner-device-timed (OA-2)**, evidenced by the x86_64 linker64 proof (both API levels) plus the mechanical argument (a static arm64 ELF through the arm64 linker is the mainstream zygote-child shape); the documented fallback on an arm64-device failure is the CGO external-link arm64 rebuild (re-pins S0's hashes/sizes/recipe — S0-owned, not a code change).
- **`PtInstallDeviceTest` updated for rev 3** (re-run on API 35 + API 29 this session: green both — `device tests: 1 run, 0 failed, 0 skipped`, report lines below): the own-ABI linker64-exec assertion stays (x86_64 gate images: exit 0, `lyrebird 0.9.0`); the arm64 half now extracts the arm64 asset (the test APK ships both ABIs) and asserts the through-linker exec **on arm64(-capable) devices** — the OA-2 on-device half pinned in code — while on a non-translation host it records the exact outcome (`exit=1, EM_AARCH64 vs EM_X86_64`) and the reason without asserting (a JUnit skip would count as a failure under this runner, the §15.9 rule). Both levels record identically: `pt-device: direct exec: denied: … error=13, Permission denied`; `pt-device: own-abi (x86_64) linker64 exec: exit=0 lyrebird 0.9.0`; `pt-device: arm64-through-linker64: exit=1 error: "…" is for EM_AARCH64 (183) instead of EM_X86_64 (62)`; `pt-device: arm64 exec not asserted on this host: abi=x86_64, abilist=x86_64[, x86] — no ARM translation here; the arm64 exec stays owner-device-timed (OA-2)`.
- The probe pins today's truth in code: the direct exec **must** be refused, the own-ABI linker path **must** answer, and the arm64 path must answer wherever an arm64 ELF can actually run here.
