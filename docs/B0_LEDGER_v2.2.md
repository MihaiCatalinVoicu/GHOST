## 2. Clasele de blocaj folosite în matrice

| Clasă | Sens | Cine o ridică |
|---|---|---|
| EXEC | Implementabil acum: cod, design, teste locale (WSL/emulator), documente | agentul, fără input extern |
| DEVICE | Cere dispozitive fizice (telefoane, radio, al doilea mediu de build) | proprietarul pune la dispoziție |
| 3P | Cere terți (auditori, counsel/editor, testeri umani, includere Sigsum live, GMS-free hardware cumpărat) | contractare/recrutare |
| OWNER | Decizie sau achiziție a proprietarului (token-uri hardware, domeniu, buget audit, autorizare lansare, Q3/Q18) | decizie scrisă |

Regula obiectivului curent al proprietarului: se lucrează tot ce este EXEC, în ordinea
roadmap-ului, astfel încât la final să rămână exclusiv DEVICE/3P/OWNER. Ledger-ul se actualizează
la fiecare pachet închis.

### Corectare decizie MD-5 (2026-12-12, la analiza de implementare)

### Scoping MD-6 și A-2 (2026-11-12) — ambele necesită un API de bracketing sesiune

**MD-6** (consume inbox în timpul bandei): coada (`consumerTail`, DmActor:358) rulează deja un pass complet la sfârșitul sesiunii de fundal/quiet — consumul DIN COADĂ există. Necesită: punctul de sfârșit de sesiune pentru FOREGROUND (consumerTail acoperă doar BACKGROUND/QUIET — `require(kind == BACKGROUND || QUIET)`) — deci un callback de end de sesiune din runtime (MessagingWiring știe ciclul de viață al sesiunilor pentru entitlement engine).

**A-2** (wakelock alarmă): `ExpiryAlarmReceiver` face `goAsync(); onAlarm?.invoke(); pending.finish()` — wakelock-ul cade înaintea sweep-ului postat. **Fix**: `onAlarm` devine `((onDone: () -> Unit) -> Unit)?`; wiring-ul propagă onDone prin `onTimeTrigger(onDone)` (DmActor.wake primește un callback rulat pe firul actorului după runPass, în `finally`); receiver-ul amână `pending.finish()` până la onDone (cu nota bugetului goAsync — sistemul eliberează oricum la limita lui). Calea fără stack (`whenStoresOpen`) are semantica ei de completare (open + pass) — același callback.

**Pattern comun**: ambele au nevoie de semnale de completare/bracketing între runtime și actor — se implementează împreună într-o felie dedicată cu `MessagingWiring` și testele lui la îndemână (`MessagingWiringTest`, `MessagingWiringRuntimeTest` vor prinde schimbările de semnătură).
